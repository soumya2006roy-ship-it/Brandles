# Product implementation decisions

## Architecture choices for the remaining delivery phases

- Preserve the completed Phases 1–8 and continue at Phase 9. Phase 9 uses the existing pytest/FastAPI suite, adds frontend Vitest unit tests and Playwright journeys, and uses GitHub Actions PostgreSQL/Redis service containers for integration and migration checks. Tests that need Docker remain an explicit local prerequisite; CI provides its own disposable services.
- Keep runtime observability dependency-light: emit one JSON log record per API request with a generated or validated request ID, provide `/health` for process liveness and `/ready` for PostgreSQL/Redis readiness, and expose bounded Prometheus-format request, job and LLM-cost counters. Add an optional Sentry-compatible DSN integration through environment configuration; errors continue to log if Sentry is absent.
- Phase 10 uses a standalone Next.js image and a shared Python API/worker image with distinct commands. Keep development Compose for hot reload, add a production Compose file with readiness health checks and release migrations as a separate one-shot service, and document managed-service deployment as an operator choice rather than claiming a specific provider was provisioned.
- Keep migrations explicit and backward-compatible. `alembic upgrade head` is the release step; rollback instructions must distinguish application rollback from destructive schema downgrade. Document database and object-store backups and a restore rehearsal.
- Keep model-provider integrations disabled by default. Retrieval uses exact lexical matching and deterministic lexical-hash vectors; no synthetic judgement provider is registered at runtime. OCR and malware scanning remain optional and unavailable until configured.

## Existing architecture decisions

- The public fictional-workspace path is removed. Organisation data is available only after account authentication and tenant authorization; visitors use organisation creation, login, invite redemption and contact entry points.
- Preserve the historical migration chain. Migration `0009_remove_public_workspace_marker` marks existing public-example organizations deleted, then drops the obsolete marker column without changing migration `0006` or its checksums.
- `start.bat` is the Windows full-stack entry point; `start-brandlens.bat` delegates to it. It runs native API, worker and web processes, and uses Docker Compose only for Postgres/pgvector, Redis, MinIO and Mailpit. It waits for data-service health and API/web HTTP readiness. `start.sh` and `npm run dev:all` provide the corresponding cross-platform entry. Local first-admin bootstrap reads generated development credentials from `.env` and is idempotent.
- Runtime LLM and embedding providers default to `none`. The fixed insufficient-evidence client exists only in the evaluation runner and cannot be selected by application settings.
- Phase 2 of the website cleanup removes the unauthenticated public workspace route, its API/seed path, and runtime deterministic provider stand-ins. Migration `0009_remove_public_workspace_marker` tombstones legacy example organizations before removing the marker; it was not applied locally because a database service is unavailable.
- Phase 3 adds `/signup`, `/org/create`, and `/join` aliases, enforces a current API session under `/app/*`, and keeps browser API requests same-origin through one server-configured backend URL. Phase 4 adds the native full-stack launcher, stop/reset helpers, health gates and local admin bootstrap. The full stack remains unverified until Docker is available.
- Interactive FastAPI documentation is served at `/docs` in development and the schema at `/api/openapi.json`; production disables both. The launch verification record distinguishes isolated SQLite endpoint smoke from Postgres/Redis-backed startup.

The user-provided product brief defines campaign scans, evidence-backed findings, campaign-level comparison, resolution and reviewer approval. Implementation follows these requirements while preserving explicit prototype limits.

- The existing BrandLens public site and its content remain grounded in `docs/brandlens-proposal.md`. Product assumptions do not create new customer claims or pricing.
- The site and API run as separate Next.js and FastAPI services. PostgreSQL with pgvector stores tenant-scoped records; Redis provides shared queue/rate-limit infrastructure; local compose provisions private MinIO and Mailpit.
- A user must verify email to authenticate. New organisations are pending review. A platform operator grants administrator status via a trusted CLI after database access, and cannot approve their own submitted organisation.
- Invitations are random, expiring, role-scoped and use-limited. Only a one-way hash is persisted. Sessions use HTTP-only cookies and password hashes use Argon2id.
- Source documents are parsed with PyMuPDF and python-docx, chunked with overlap, and stored with page/location references. The current local vector is a deterministic lexical hash representation for prototype retrieval, not a semantic embedding model.
- Only Admin-approved source versions with effective dates are current evidence. New versions archive earlier approved versions for that source family, and rules tied to superseded versions are archived. Creator-created rules remain suggestions until Admin approval.
- No live model adapter is present. If a future adapter is added, both deployment and workspace permission gates must allow it. Judgement responses use a strict Pydantic contract, and citations/flagged spans are checked against retrieved passages and asset text. The deterministic insufficient-evidence fixture is restricted to evaluation code.
- Retrieval ranks approved effective passages using the stored deterministic lexical-hash vectors. These are not semantic embeddings. A claim without a validated judgement is surfaced as `Needs human verification`, never as a breach.
- Campaign scans run through the Redis worker, persist their asset-version and active-rule snapshots before processing, expose per-asset progress, and support cancellation and checkpointed resume. One scan per organisation runs at a time; default limits cap assets, judgement candidates, and total scan duration. Any future provider adapter must also enforce its configured per-request timeout. A failed provider check falls back to human verification.
- Deterministic checks cover approved offer names and discounts, validity dates, banned phrases, required disclaimers, channel limits, language-scoped parameters, and prototype logo comparisons. Facts extract percentages, currency values, dates, and claim sentences; values are normalized where formats are unambiguous. Conflicts and facts without evidence are review prompts, not breaches.
- Findings support filters by severity/type/status/channel, grouping, evidence details and suggested-text comparison. Creator edits create a new asset version, while dismissal requires a reason and clarification is routed to Admins. Review submission is idempotent; decisions are stored against exact asset versions and scan snapshots, and new assets stale prior scan evidence. Reviewers cannot decide their own submissions. In-app notifications and configured email messages cover review events, organisation verification and invitation redemption. There is no automatic rewriting or platform publishing.
- The Evidence Map shows cited approved passage text, source version and page/location. Assets that mention an approved offer outside its rule/source effective dates receive a warning based on the planned publish date.
- Repeated resolution/dismissal of the same normalized pattern creates an Admin-facing guideline update suggestion after three feedback events. Accept/ignore is audited, and accepting does not change policy or rules.
- Brand Twin is an extractive, retrieval-only Q&A over effective approved passages. It requires textual overlap with the question, cites every excerpt, and refuses when no passage matches. It does not call an LLM.
- Hindi phrase checks and lexical retrieval use the same deterministic text and hash-vector code paths. This is a limited-accuracy prototype, not translation or semantic multilingual evaluation. Instagram/LinkedIn-style preview cards display character counts, hashtags, links and truncation only when an approved channel limit exists; platform rendering is not emulated exactly.
- The product workspace dashboard derives its counts from current scans, pending review submissions, recent campaigns and approved offers. Findings and audit-event lists are organization-scoped, bounded and paginated. The audit view exposes action metadata, not source or asset contents.
- Product access requires an account. Visitors can create an organisation, log in, join through an organisation invite or contact the team. No unauthenticated workspace data is exposed.
- Per-membership notification preferences control in-app and email notices. The AI processing setting and notification preferences are available in workspace settings; no external AI provider is connected.
- Campaigns scope channels, dates and language. Each asset group retains immutable versions; replacing an asset marks asset-level and campaign-level scans stale and their findings stale.
- Upload types are detected from signatures/content rather than filename extensions. Files have size limits, optional ClamAV scanning fails closed when configured, and accepted raster images are re-encoded without metadata.
- PDF and DOCX text extraction is enabled for assets. OCR is behind a provider interface and may use Tesseract when configured. Prototype approved-logo matching uses perceptual difference hashes against approved image source versions and is not a vision model.
- Storage drivers use private local/S3-compatible paths and organization-scoped access; source and campaign asset upload/download are enabled.
- Docker Compose is the complete local launch path. `npm run dev` intentionally starts only the public website; the Windows launcher must not silently fall back to it when full-stack prerequisites are unavailable.
- Labelled evaluation fixtures cover the skincare offer conflict and an unsupported claim. The evaluation script reports exact finding-type precision/recall, citation validity, and false-breach rate; it runs with SQLite and an evaluation-only deterministic fixture.
- The backend has test coverage using SQLite and fake email. Production use still requires infrastructure configuration, a security review, and a real provider adapter if model judgement is desired.
- Browser mutation requests reject mismatched Origin and cross-site Fetch Metadata. The Next.js API proxy forwards these headers; no permissive CORS policy is enabled. Production session cookies are secure and HTTP-only, and both apps emit security headers. The API only trusts forwarded client IP values from explicitly configured proxy CIDRs; the ingress must overwrite incoming forwarding headers.
- Redis provides expiring shared request counters for authentication, organization registration, invite redemption/creation, uploads, scan creation, export/deletion and Brand Twin. Exceeded limits return `429` with `Retry-After`; production returns `503` when Redis is unavailable. Login failures add progressive retry delays capped at one minute and the failure state expires; successful login clears it, so accounts do not receive permanent lockouts.
- Auth and workspace audit events are append-only. ORM flush checks protect all environments and migrations add SQLite/PostgreSQL update/delete triggers. Audit metadata omits raw document text, invite codes, secrets, comments and clarification text; organization deletion retains the audit rows and a soft-deleted anonymized organization shell.
- Admins can download a JSON export including original uploaded files up to 100 MB, set scan/finding history retention from 30 to 3,650 days, or delete an organisation after entering its exact name. A worker purges expired completed scan, finding and review details hourly. Current sources/assets and identity accounts are retained until workspace deletion; audit history is retained after deletion.
- CI checks npm and Python dependency advisories and scans Git history with Gitleaks. Findings still require triage; these automated scans do not replace security review.
